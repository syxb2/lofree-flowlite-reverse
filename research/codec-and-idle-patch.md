## 1. 编码与检查值

程序区仍从容器偏移 `0x2000` 开始。其编码是逐字节模 256 加法，密钥每 32 字节循环：

```text
91 cd e4 69 96 45 5a 63 9a 8c c9 4c c9 82 23 15
37 38 29 18 f9 f8 e6 e1 55 5a a5 6b b8 b2 ac bc
```

\[C_i = (P_i + K_{i\bmod32})\bmod256\]

\[P_i = (C_i - K_{i\bmod32})\bmod256\]

密钥由程序区 `0xe0..0xff` 的重复填充块获得，随后以全部八个不同参考镜像的检查值验证。
解码后出现连续 RISC-V 压缩指令、USB 描述符和 `Air84@Lofree`、`Flow84-L@Lofree`、`Compx` 字符串。
此前只使用 Cortex-M 栈/复位向量启发式，因此漏掉了 RISC-V，不能将先前筛选无结果理解为编码难以还原。

准备命令中的大端 32 位检查值实际是：

```python
device_check = zlib.crc32(decoded_program) ^ 0xffffffff
```

这是标准 CRC-32/ISO-HDLC 的最终异或前状态。
v1.66 明文 CRC32 为 `0x263418e1`，取反得到原包的 `0xd9cbe71e`。
八个镜像均通过该关系与解码/重编码逐字节往返验证。

容器头仍使用 `0x55555555 - sum(container[8:720])`；这是另一层校验。
代码见 `../tools/oe921_codec.py`，证据见 `firmware/analysis/oe921-v166-codec.json` 和 `codec-cross-validation.json`。

## 2. CPU 映射和 XW 指令

写入地址 `0x08001600` 是升级协议中的 Flash 地址；程序中的 CPU 地址使用低地址别名 `0x1600`。
首指令 `0x6110b06f` 是跳至 `0xd410` 的 RISC-V `jal zero`。
该启动代码通过 PC 相对计算建立 `gp=0x20000820`、`sp=0x20005000`，将 ROM `0xf1f4..0xf273` 的 128 字节复制到 RAM。
低地址映射使这些计算和向量表中的地址一致。分析 ELF 包装器由工具生成，不是可刷写固件。

程序使用 WCH/青稞 XW 的压缩字节/半字访存指令；标准 RISC-V 解码会将部分指令误解为浮点访存。
项目内新增独立语言 `RISCV:LE:32:OE921_XW`，保留原 Ghidra RISCV 文件。
XW 定义采用 [Ghidra PR #6390](https://github.com/NationalSecurityAgency/ghidra/pull/6390) 的实现，并与 [LLVM 的 Xwch 编码定义](https://github.com/llvm/llvm-project/blob/main/llvm/lib/Target/RISCV/RISCVInstrInfoXwch.td) 交叉核对。
适配后导出 259 个非 thunk 函数，导出失败为 0，未再出现原标准解码的 pcode 错误。
共享寄存器保存/恢复辅助函数被标记为分析时内联，并对经 t0 返回的辅助代码设置返回流覆盖；这些只改变 Ghidra 分析元数据。

## 3. 定位到的计时链

| 地址/变量 | 作用 |
| --- | --- |
| `0x8b80` | 重置空闲倒计时；模式 0 采用 6 个周期，非 0 分支采用 60 个周期 |
| `0x2000032e` | 当前模式；主状态机区分模式 0、1..5、10、有线之外的其他状态 |
| `0x2000011c` | 每周期 10,000 个定时器中断，16 位倒计时 |
| `0x2000011e` | 剩余周期数，8 位无符号读写 |
| `0x2000011f` | 重载周期数 |
| `0x20000118` | 周期耗尽后设置的空闲超时标志 |
| `0xc772` / `0xc822..0xc85b` | TIM3 中断中的空闲计时递减代码 |
| `0xca04` | TIM3 配置，预分频 47、重装载 999，对应 48 MHz 时钟下的 1 ms 中断 |
| `0x917c` | 已连接无线工作循环；超时后转入状态 0 |
| `0x9338` → `0x8f84` → `0x85e8` | 无线状态机的休眠路径，后者发送协议命令 `0x0b` |
| `0x20000190` / `0x20000192` | 独立背光计时变量，位于同一 ISR 的后续代码，未修改 |

Fn 通道按下/长按处理在 `0x9b2a` 调用 `0x98ec`，以 1/2/3 选择对应无线通道，以 0 选择另一无线模式；主循环单独处理模式 10。
这些软件关系支持模式 0 为 2.4G、1..3 为蓝牙通道的判断；此次没有读取实物模式状态进行交叉验证。

原有主控计时为 `60 × 10000` 中断，即约 600 秒；改后为 `180 × 10000`，即约 1800 秒。
180 在 8 位无符号范围内，机器码执行验证也覆盖大于 127 的值，避免有符号截断误判。

## 4. 两处最小修改

| CPU 地址 | 容器偏移 | 原指令 | 新指令 | 原因 |
| --- | --- | --- | --- | --- |
| `0x8b88` | `0x9588` | `li a4,60` / `13 07 c0 03` | `li a4,180` / `13 07 40 0b` | 非零无线分支的最大空闲周期增加三倍 |
| `0x92b8` | `0x9cb8` | `li a4,54` / `13 07 60 03` | `li a4,174` / `13 07 e0 0a` | 保持已有提前低功耗检查的实际触发时点 |

第二处仅在模式 1..5 的分支使用。原检查条件是剩余周期不大于 54，即经过 6 个周期后开始评估 `0x5f14`。
将最大周期从 60 增加到 180 后，把门限同时加 120，检查仍在 6 个周期、约 60 秒后生效。
不补偿该值会让这条既有检查延迟约 20 分钟。
该路径在符合条件时设置 `0x20000113`，跳过 `0x85e8` 的无线模块休眠请求；此次保留该行为。

程序区实际仅 4 字节变化；重算整包检查值和容器头校验后，完整容器总计 10 字节不同。
文件大小、版本字段、CID/MID、写入地址、端点和全部其他程序字节保持原样。
背光计时、熄灯阈值存储、按键唤醒、重连指令和模式 0 的计时常量没有修改。

候选整包检查值：`0x1967a126`；容器头校验：`0x555524c5`。
精确偏移及 SHA-256 记录在 `../output/patch-manifest.json`。

## 5. 已完成的验证

1. 八份参考容器均通过明文 CRC 和编解码往返验证。
2. 补丁构建锁定原厂 v1.66 的完整 SHA-256，并校验两条原指令；不同输入及重复补丁被拒绝。
3. 从原文件重建的候选文件逐字节相同；候选重新解码与预期明文完全一致。
4. 对全部程序字节检查：只有两条指令中合计 4 字节变化；独立背光计时 ISR 及其他全部代码逐字节相同。
5. 错误头校验和程序区单字节损坏均被解码器拒绝。
6. `verify_idle_machinecode.c` 执行原/新实际指令，覆盖模式 0..5，确认超时分别为 60,000 / 600,000 / 1,800,000 个中断，重载清除超时标志；提前检查在原/新程序中均于 60,000 个中断开始。
7. Ghidra 对修改后 ELF 独立确认两条 `li` 指令，并重新反编译重载、无线循环和计时 ISR 三个函数。

执行验证是受限 RV32/XW 指令解释器，只覆盖选定计时路径；未模拟外设、蓝牙射频协议、功耗或完整键盘。

## 6. 第一版实机验证与局限

这份补丁能够确定改变主控中的空闲超时；不能据此保证外部无线模块没有独立的 10 分钟休眠策略。
提前低功耗路径也与无线模块状态有关，必须通过实际蓝牙连接观察确认最终效果。
未进行完整设备固件备份或失败恢复实测。实际刷写和 USB 交互已完成，见第 8 节。

写入前通过只读 USB/HID 枚举确认 `Air84@Lofree / Compx`、`05ac:024f`、`bcdDevice=0x0166`，与目标正常端点和版本一致。
没有读取实物 CID/MID；正常固件进入 BOOT 并升级的路径已验证，故障恢复条件仍未实测。
后续用户在未开背光、拔掉 USB 的条件下反馈仍约 10 分钟断连，因此本版未达成目标。
进一步定位到蓝牙分支向无线侧发送 `0x0C`、参数 `58 02`（600）；第二版把它改成 `08 07`（1800），保留本报告的主控补丁，随后用户确认目标生效。
